# Syntra Build — AGENTS.md

## 1. Purpose

This file defines the durable engineering rules that coding agents must follow when working on Syntra Build.

`SPEC.md` defines **what must be built**.

`AGENTS.md` defines **how implementation work must be performed**.

These rules apply to:

- initial bootstrap development performed manually through the Human → Architect → Codex → GitHub workflow;
- later work orchestrated by Syntra Build itself;
- implementation work;
- CI rework;
- Architect-review rework;
- human-test rework;
- maintenance changes unless an approved specification revision explicitly overrides a rule.

A coding agent must read this file and the relevant milestone in `SPEC.md` before modifying the repository.

---

## 2. Authority and Source Precedence

When instructions conflict, use the following precedence:

1. explicit human decisions recorded after the existing design;
2. accepted Architecture Decision Records;
3. approved `SPEC.md`;
4. this `AGENTS.md`;
5. approved architecture/security/interface/data-model/workflow/operations documents;
6. the current milestone task;
7. implementation assumptions.

A milestone task may narrow the work required by `SPEC.md`.

A milestone task must not silently override architecture, security, data-integrity, or trust-boundary rules.

If a task appears to require violating a higher-priority rule, do not invent a workaround. Report the conflict.

Two superseding project decisions must always be respected:

- Syntra Build uses **Python 3.14**, with package metadata targeting `>=3.14,<3.15`.
- **GitHub** is the canonical source-control platform for Syntra Build itself and for projects generated by Syntra Build.

Older Python 3.12 or Forgejo references in historical design documents are superseded.

---

## 3. Agent Role

The coding agent is an **implementation worker**.

The coding agent is responsible for:

- understanding the assigned milestone;
- inspecting relevant repository files;
- implementing the smallest complete change that satisfies the milestone;
- adding or updating tests;
- running appropriate local validation;
- correcting defects;
- responding to CI findings;
- responding to Architect review findings;
- leaving the assigned worktree in a coherent state;
- providing an accurate implementation summary.

The coding agent is not the workflow controller.

The coding agent must not decide that:

- a milestone is approved;
- CI is sufficient when required checks have not passed;
- human testing may be skipped;
- a pull request may merge;
- project state may advance;
- a security control may be bypassed.

Those decisions belong to Syntra Build and its deterministic policy layer, with Architect/human input where defined.

## 4. Core Engineering Principles

All implementation must preserve these principles.

### 4.1 Syntra owns state

Authoritative workflow state is owned and persisted by Syntra Build.

AI conversation state, process memory, logs, Git branches and GitHub state are not substitutes for authoritative Syntra state.

### 4.2 Persist before side effects

A workflow transition that leads to an external side effect must be durably recorded before the side effect is initiated.

### 4.3 Reconcile before replay

External operations that may already have succeeded must be inspected/reconciled before retry.

Do not implement blind retry logic for operations such as:

- repository creation;
- branch push;
- PR creation;
- merge;
- human-gate creation/notification.

### 4.4 AI output is untrusted input

Architect and Codex responses must be validated before they can cause authoritative state changes.

Free text must not directly trigger privileged operations.

### 4.5 Keep privilege deterministic

Repository creation, accepted commits, pushes, PR creation, merge, visibility changes, workflow-state changes and human-gate resolution must be controlled by normal deterministic code.

### 4.6 Prefer simple mechanisms

Version one is deliberately a single Python service.

Do not introduce distributed infrastructure merely because it might be useful later.

### 4.7 Build for recovery

Every asynchronous or externally visible operation must be understandable after a process or host restart.

### 4.8 Project isolation

One project must not accidentally resolve, mutate or consume another project's resources.

### 4.9 Exact revision matters

CI, Architect approval and human-test evidence must be associated with the exact applicable code revision.

### 4.10 Tests are part of the implementation

A deterministic behaviour is incomplete until its important success and failure paths are tested.

## 5. Runtime and Platform

### 5.1 Python

Supported runtime:

```text
Python >=3.14,<3.15
```

Do not add compatibility work for Python 3.12 or 3.13 unless an approved specification revision explicitly requires it.

Do not use syntax or APIs that require Python 3.15+.

### 5.2 Host platform

The production control plane targets:

```text
Linux ARM64
Ubuntu on Raspberry Pi
```

Code that runs on the Syntra host must use dependencies that support Linux ARM64.

Generated projects may target other platforms; Syntra Build itself does not need to run natively on Windows or macOS.

### 5.3 Heavy cross-platform work

Do not turn the Raspberry Pi into a cross-platform build farm.

Heavy or target-specific build/test work belongs in GitHub Actions where practical.

## 7. Architectural Boundaries

### 7.1 Domain layer

The domain layer contains:

- workflow states;
- durable domain identifiers;
- domain rules;
- transition rules;
- domain events;
- validated domain contracts/value objects where appropriate.

The domain layer must not import:

- Telegram SDKs;
- GitHub SDKs;
- OpenAI/provider SDKs;
- Codex-specific process code;
- HTTP frameworks;
- systemd-specific code.

The domain must remain testable offline.

### 7.2 Application layer

The application layer coordinates use cases such as:

- project creation;
- transitions;
- scheduling;
- status projection;
- recovery;
- Gatekeeper evaluation.

It may depend on domain abstractions and adapter interfaces.

It must not depend directly on provider response formats.

### 7.3 Adapter layer

Adapters translate between external/provider-specific data and Syntra contracts.

Provider-specific schemas belong here.

Examples:

- Telegram update JSON;
- GitHub API responses;
- Architect provider envelopes;
- Codex CLI output.

Do not leak these representations into core workflow code.

### 7.4 Infrastructure layer

Infrastructure owns technical facilities such as:

- SQLite;
- configuration;
- filesystem access;
- subprocess execution;
- logging;
- metrics.

Business workflow policy must not be hidden in infrastructure helpers.

## 8. Dependency Direction

Preferred direction:

```text
external systems
      ↓
   adapters
      ↓
 application
      ↓
    domain

infrastructure supports application/domain through explicit interfaces
```

Avoid circular imports.

Do not make the domain depend on adapters.

Do not make state-transition correctness depend on Telegram, GitHub or an AI provider being available.

## 9. Coding Style

### 9.1 General

Write code for clarity and auditability.

Prefer:

- explicit names;
- small focused functions;
- typed interfaces;
- explicit enum/state values;
- visible control flow;
- dataclasses or validated models for structured contracts;
- composition over clever inheritance.

Avoid:

- metaprogramming without a strong reason;
- hidden global state;
- dynamic monkey-patching;
- broad exception swallowing;
- magic string state transitions;
- deeply nested control flow;
- abstractions added only for hypothetical future needs.

### 9.2 Type hints

New production Python code should be type annotated.

Public functions and cross-component contracts require useful type annotations.

Avoid `Any` where the structure is known.

Provider raw payload boundaries may use broader types temporarily, but normalised domain objects must be typed.

### 9.3 Enums

Workflow states and verdicts must use explicit enums or equivalent validated constants.

Do not compare authoritative states using arbitrary strings scattered throughout the codebase.

### 9.4 Datetimes

Persist and exchange timestamps in UTC.

Use timezone-aware datetimes.

Do not rely on local host timezone for persisted workflow semantics.

### 9.5 Identifiers

Use stable internal Syntra IDs for domain identity.

Human-readable project names, repository names, PR numbers and external IDs must not replace internal primary identity.

---

## 10. Error Handling

Errors must be explicit and classifiable.

Differentiate at least:

- validation failure;
- invalid state transition;
- configuration failure;
- transient external failure;
- permanent external failure;
- retry exhaustion;
- policy/security failure;
- integrity/reconciliation ambiguity;
- user/human action required.

Do not use one generic exception path to decide workflow state.

Do not mark an operation successful because no exception was raised if external outcome still needs verification.

Messages shown to the human must be useful without exposing secrets.

---

## 11. Persistence Rules

### 11.1 SQLite

SQLite is the version-one state store.

Required database behaviours include:

```text
journal_mode = WAL
foreign_keys = ON
```

Use explicit migrations.

Do not modify a released schema manually without a migration.

### 11.2 Transactions

Current state and the transition/history record that produced it must be updated atomically where required.

A partial write that creates inconsistent authoritative state is unacceptable.

### 11.3 History

Transition/event/audit history is preservation-oriented.

Do not rewrite old events simply to make current results look cleaner.

### 11.4 JSON fields

Use JSON for flexible provider metadata or optional extension detail.

Do not hide important queryable workflow identity/state inside opaque JSON.

Fields such as these should be explicit:

- project state;
- milestone state;
- job state;
- gate state;
- repository identity;
- PR number;
- SHA;
- retry count;
- timestamps needed for scheduling.

### 11.5 Migrations

Every schema-changing PR must include:

- forward migration;
- tests from a clean database;
- tests upgrading from the previous schema when relevant;
- rollback/recovery notes if the migration is not backwards compatible.

---

## 12. State-Machine Rules

The state machines in `SPEC.md` and `STATE_MACHINE.md` are authoritative.

Do not invent new states inside an implementation milestone without an approved spec/design update.

All state transitions must:

1. validate current state;
2. validate requested target state;
3. validate required guards/evidence;
4. persist the transition;
5. only then trigger subsequent side effects.

Invalid transitions must fail visibly.

Do not add permissive catch-all transitions to simplify implementation.

Architect verdicts such as `APPROVE` are events/verdicts, not implicit workflow states.

---

## 13. Asynchronous Jobs

Jobs and project/milestone states are separate.

A project may remain `BUILDING` while a job is `WAITING_EXTERNAL`.

Implement job execution so:

- jobs have stable IDs;
- attempts are numbered;
- prior attempts remain available;
- terminal attempts are immutable;
- transient retries use durable retry timing;
- lost processes can become `ABANDONED`;
- external waits do not occupy scarce local worker slots.

Do not implement an in-memory-only queue as the authoritative job system.

---

## 14. Scheduler Rules

Scheduler behaviour must remain deterministic and resource-bounded.

Initial configurable defaults:

```text
Architect concurrency: 2
Codex concurrency: 2
Repository provisioning: 1
Merge concurrency: 1
```

Rules:

- paused projects receive no new implementation work;
- cancelled projects receive no new work;
- one active implementation milestone per project in version one;
- projects waiting for CI/human/retry do not occupy Codex slots;
- fairness must prevent a failing project from monopolising worker capacity;
- resource guards may temporarily prevent new Codex dispatch.

Do not hard-code limits where configuration is required by `SPEC.md`.

---

## 15. Telegram Rules

Telegram is an adapter, not a domain.

### 15.1 Authorisation

Use stable Telegram IDs.

Do not authorise based solely on:

- username;
- display name;
- free-text project name.

### 15.2 Duplicates

Telegram updates may be delivered more than once.

Duplicate delivery must not create duplicate state-changing actions.

### 15.3 Secrets

Never:

- log the bot token;
- persist it in project data;
- place it in prompts;
- expose it to Codex;
- send other credentials through Telegram.

### 15.4 Commands

Read-only commands must not mutate project state.

State-changing commands must be:

- authorised;
- resolved to an exact project/gate;
- validated;
- persisted before action.

### 15.5 User experience

Responses should be concise and operationally useful.

Do not dump raw provider JSON, tracebacks or large logs into Telegram.

---

## 16. Architect Adapter Rules

The Architect is advisory.

The adapter must:

- translate provider responses to validated Syntra contracts;
- reject malformed workflow-changing responses;
- persist relevant provider request/response metadata;
- use explicit timeouts;
- support retries of transient failures;
- bind code reviews to exact PR head SHA.

The Architect must not receive:

- GitHub administrative credentials;
- Telegram token;
- host secrets;
- direct database mutation access;
- shell access to the Syntra host.

Do not implement a path where Architect prose directly invokes Git/GitHub operations.

---

## 17. Codex Runner Rules

Codex is an untrusted execution component.

### 17.1 Execution identity

Codex must run separately from the trusted Syntra control plane using the dedicated unprivileged execution identity defined by the security design.

### 17.2 Workspace

Codex receives only the assigned worktree and minimum supporting context.

Codex must not require write access to:

```text
/opt/syntra-build
/etc/syntra-build
/var/lib/syntra-build
/var/log/syntra-build
```

except explicitly assigned non-control-plane workspace paths.

### 17.3 Credentials

Codex must not receive privileged:

- GitHub credentials;
- Telegram credentials;
- control-plane secrets;
- database access;
- credentials for unrelated systems.

Codex may receive only the coding-provider authentication required to run Codex itself.

### 17.4 Git

Codex may inspect:

```text
git status
git diff
git log
```

where useful.

Codex must not rely on creating accepted commits.

The authoritative deliverable is the changed filesystem worktree.

### 17.5 Local commands

Codex may run reasonable project-local:

- tests;
- linters;
- static checks;
- build commands;
- dependency install commands within approved project environments.

Codex must not:

- use `sudo`;
- install host packages casually;
- invoke `systemctl` to change host services during implementation;
- access Docker socket;
- add itself to privileged groups;
- run arbitrary remote install pipelines such as `curl ... | sh`.

Host-level operational steps belong in reviewed deployment/setup instructions.

---

## 18. Git and GitHub Rules for Coding Agents

During normal Codex implementation:

**Do not:**

- push;
- force-push;
- create repositories;
- delete repositories;
- create PRs;
- merge PRs;
- close PRs;
- alter branch protection;
- change repository visibility;
- create or change GitHub secrets;
- administer GitHub Actions settings;
- tag or create releases unless an explicitly approved task and trusted control path require it.

Syntra/trusted orchestration performs privileged GitHub actions.

During the manual bootstrap phase, a human-controlled workflow may perform those operations outside Codex, exactly as with FlowTrack.

The coding agent must not treat the existence of local GitHub credentials as permission to use them.

---

## 19. Change Validation Rules

Before a Codex-produced change is accepted, trusted Syntra logic will validate it.

Code must support checks for:

- expected project;
- expected repository;
- expected remote;
- expected branch;
- expected base/head SHA;
- unexpected Git-history changes;
- branch substitution;
- worktree escape;
- protected path changes;
- secret findings;
- exact diff/hash identity.

Do not build workflows that assume Codex's completion message proves what files changed.

Filesystem/Git evidence is authoritative.

---

## 20. Protected Paths

Changes to security-sensitive paths require explicit milestone scope and additional validation.

Examples include:

```text
.github/workflows/
.github/actions/
deployment/
scripts affecting service installation
security policy/configuration
secret handling
authentication
release/signing configuration
```

A coding agent must not modify protected files opportunistically because a local test would otherwise be easier to pass.

If a protected path genuinely needs changing, the task/PR should make that visible.

---

## 21. Secret Handling

Never commit real credentials.

Never add real secrets to:

- source files;
- fixtures;
- Markdown examples;
- `.env` committed files;
- test snapshots;
- logs;
- exception messages.

Tests for secret detection must use synthetic unmistakably fake fixtures.

Do not weaken secret detection to make a test or milestone pass.

If a real credential is discovered:

- do not reproduce it in output;
- do not commit it;
- surface the finding safely.

Private repository status is not permission to commit credentials.

---

## 22. GitHub Actions Rules

GitHub Actions is the authoritative hosted CI environment for required CI.

Every implementation PR must preserve required CI.

Do not:

- disable a failing required check;
- add `continue-on-error` merely to make CI green;
- reduce test coverage to hide a defect;
- change workflow triggers to avoid running tests;
- remove Python 3.14 CI;
- expose repository secrets to untrusted PR code.

Workflow changes must be justified by milestone scope.

Local passing tests do not replace required GitHub Actions results.

---

## 23. Test Strategy

### 23.1 Test levels

Use:

- **unit tests** for domain rules, models, transitions and pure application logic;
- **integration tests** for SQLite, filesystem/Git adapters and multi-component flows;
- **adapter tests** using fake/stub external provider responses;
- **live integration tests** only when external credentials/services are genuinely required.

Normal PR CI should run without live Telegram/GitHub/AI credentials wherever possible.

### 23.2 Determinism

Tests must not depend unnecessarily on:

- wall-clock sleeps;
- public network connectivity;
- random timing;
- external API availability.

Inject clocks/IDs/adapters where deterministic testing improves correctness.

### 23.3 State-machine coverage

Each state-machine milestone must test:

- valid transitions;
- invalid transitions;
- guard failures;
- atomic history/current-state behaviour.

### 23.4 Negative tests

Security and recovery controls require negative-path tests.

Examples:

- unauthorised Telegram sender;
- stale CI SHA;
- stale Architect review SHA;
- duplicate gate response;
- repository identity mismatch;
- secret finding;
- invalid transition;
- duplicate PR creation event;
- lost Codex process;
- ambiguous merge result.

### 23.5 Regression tests

When fixing a defect, add a regression test when the defect is reproducible in automated tests.

Do not fix only the symptom if the invariant can be encoded.

## 25. Dependency Policy

Add dependencies only when they materially reduce implementation risk or complexity.

Before adding a production dependency, consider:

- Python 3.14 support;
- Linux ARM64 support;
- maintenance activity;
- security history;
- license suitability;
- whether the standard library is sufficient;
- runtime footprint on the Pi;
- whether it pulls in a large dependency tree.

Avoid adding a framework for a small isolated requirement.

Pin/constraint dependencies sufficiently for reproducible CI and deployment according to the repository's chosen package-management approach.

Dependency changes must remain visible in the PR.

Do not introduce Redis, RabbitMQ, Celery, PostgreSQL, Kubernetes or similar infrastructure without an approved architecture change.

---

## 26. API and Contract Evolution

Structured workflow contracts must be versioned when persisted or externally exchanged.

When changing a contract:

- preserve existing persisted data where required;
- add migration/compatibility handling where necessary;
- update producer and consumer together unless compatibility is intentionally staged;
- reject unknown state-changing values rather than guessing.

Provider-specific fields should remain adapter-local wherever possible.

---

## 27. Logging Rules

Production logs must be structured.

Include relevant context such as:

- component;
- correlation ID;
- project ID;
- milestone ID;
- job ID;
- gate ID;
- event;
- severity.

Do not log:

- credentials;
- Authorization headers;
- private keys;
- complete sensitive environment dumps;
- unbounded provider payloads;
- unnecessary full Telegram conversation text.

Errors should be diagnosable without exposing secrets.

---

## 28. Metrics Rules

Prometheus metrics must:

- avoid high-cardinality labels such as arbitrary project names, raw SHA values or error messages unless explicitly justified;
- expose operational state, not sensitive content;
- be cheap to collect;
- remain usable if an external provider is down.

Do not put credentials, source text or human messages into metric labels.

---

## 29. Recovery Rules

Recovery code must prefer observation over assumption.

If an operation's result is uncertain:

1. inspect persisted intent;
2. inspect relevant local/external state;
3. determine whether the side effect already happened;
4. reconcile local state if certain;
5. retry only if safe;
6. block the affected workflow if uncertainty remains.

Examples:

### PR creation

Look up an existing PR for the expected branch/milestone before creating another.

### Merge

Query GitHub to determine whether merge already occurred before issuing a new merge request.

### Codex

After process loss, preserve and inspect the worktree. Do not automatically commit partial files.

### Human gate

Restore the existing gate. Do not create a new approval simply because the service restarted.

---

## 30. Human-Gate Rules

Human input must be explicit and durable.

Never infer approval from:

- silence;
- unrelated Telegram messages;
- elapsed time;
- an Architect assumption.

Responses must bind to the intended gate.

Human-test results should bind to the relevant artifact/SHA/CI revision where defined.

If code changes invalidate earlier testing, require a new test according to policy.

---

## 31. Gatekeeper Rules

The Gatekeeper is deterministic.

The coding agent must not implement shortcuts around it.

Before merge, Gatekeeper eventually verifies at minimum:

- exact project;
- exact repository;
- exact milestone;
- exact PR;
- exact branch;
- current PR head SHA;
- current required CI result;
- current Architect approval;
- required human gates/tests;
- no unresolved blocking findings;
- project is not paused/cancelled;
- no blocking security condition.

No `APPROVE` string from an AI is itself merge authority.

---

## 32. Status-Service Rules

Status is a read path.

A status query must not:

- cancel active work;
- consume a Codex worker;
- alter project state merely to answer;
- depend on AI conversational memory.

Status should derive from persisted current state and supporting execution records.

External reconciliation may update stale external observations where designed, but it must remain bounded and safe.

---

## 33. Milestone Scope Discipline

Each `SPEC.md` milestone should normally correspond to one PR.

When implementing a milestone:

### Do

- implement the required deliverables;
- implement necessary supporting code;
- add acceptance tests;
- make small refactors required for correctness;
- update documentation directly affected by the milestone.

### Do not

- pre-implement several future milestones;
- add speculative frameworks;
- redesign unrelated modules;
- opportunistically migrate technologies;
- change state semantics not required by the milestone;
- combine unrelated clean-up into the PR.

If future work becomes obviously necessary, document it rather than implementing it outside scope.

A milestone may be deliberately split if it proves too broad.

---

## 34. Rework Rules

### 34.1 CI rework

For a CI failure:

- identify whether the failure is implementation-related or infrastructure-related;
- fix the actual implementation defect when implementation-related;
- do not weaken required checks;
- add/update tests if the failure exposed missing coverage.

### 34.2 Architect rework

Address each actionable Architect finding.

If a finding is incorrect or conflicts with the spec, report the conflict rather than implementing it blindly.

### 34.3 Human-test rework

Preserve the user's observed behaviour as evidence.

Fix the issue and any root-cause regression coverage where practical.

Do not declare the human issue resolved solely because automated tests pass.

---

## 35. Documentation Rules

Update documentation when implementation changes a durable contract.

Examples:

- configuration keys;
- CLI commands;
- service installation;
- data migration behaviour;
- state semantics;
- public interface contracts;
- security requirements.

Do not rewrite architecture history just because implementation evolved.

Architectural decision changes belong in a new/superseding ADR.

Keep README operational/developer instructions concise; keep architectural rationale in design/ADR documents.

---

## 36. README Expectations

The repository README should eventually include:

- what Syntra Build is;
- supported Python version;
- development setup;
- test commands;
- configuration overview;
- how to run locally;
- production/systemd pointer;
- security warning that credentials must not be committed;
- links to `SPEC.md`, `AGENTS.md`, design documents and ADRs.

Do not duplicate the full specification in README.

---

## 37. Configuration Rules

Configuration must be typed and validated.

Do not read arbitrary environment variables throughout business logic.

Centralise loading.

Separate:

- ordinary configuration;
- credential/secret inputs.

Invalid required configuration must fail early before privileged workflow actions.

Defaults must be safe.

Path configuration must prevent accidental overlap between:

- control-plane runtime data;
- Syntra Build source worktree;
- generated project worktrees;
- secrets/config directories.

---

## 38. Filesystem Rules

Use configured roots.

Do not hard-code developer-specific home directories.

Validate canonical/resolved paths before privileged operations.

Project A paths must not resolve into Project B paths.

Worktree deletion must verify the intended managed path before recursive removal.

Never recursively delete a path derived only from untrusted project text.

---

## 39. Process Management Rules

External processes such as Codex must have:

- explicit working directory;
- controlled environment;
- timeout;
- captured exit code;
- captured stdout/stderr reference;
- process-tree termination;
- cancellation handling.

Do not launch shell commands using unsanitised concatenated user/project text.

Prefer argv-style subprocess execution over shell invocation.

Use shell execution only when genuinely required and safely constrained.

---

## 40. Time and Retry Rules

Use persisted UTC timestamps for:

- retry scheduling;
- job timing;
- gate creation/response;
- transition history.

Retry loops must be bounded.

Infrastructure retry counters must not be confused with CI/review implementation rework counters.

Do not `sleep()` for long durable retry delays while holding a worker.

Persist the next eligible time and release capacity.

---

## 41. Performance Rules

Optimise for clarity first, but preserve Pi responsiveness.

Avoid:

- polling SQLite in tight loops;
- unbounded task creation;
- loading full audit history for routine status;
- copying large Git repositories unnecessarily;
- storing large build artifacts in SQLite;
- holding Codex worker capacity while waiting for external CI.

Use indexed current-state queries for normal status views.

---

## 42. Public Repository Discipline

Generated repositories are public by default.

Implementation must therefore assume source content may become public.

Before trusted commit/push paths:

- run secret detection as required;
- ensure credentials are represented by configuration references/placeholders;
- avoid embedding host-specific private information.

Do not silently convert a project to private because sensitive content was found.

Block and surface the issue instead.

---

## 43. Syntra Self-Development Rule

Syntra Build's source lives in GitHub and may eventually be modified through Syntra Build itself.

When Syntra Build is the project under development:

- Codex works only in an isolated development worktree;
- Codex must not write into the running production installation;
- normal GitHub credential restrictions still apply;
- normal CI, review and Gatekeeper rules still apply;
- deployment/update occurs separately after merge.

Self-development is not self-modification of the running process.

---

## 44. Prohibited Shortcuts

A coding agent must never solve a milestone by:

- marking tests skipped without justification;
- deleting failing tests;
- relaxing assertions merely to pass;
- disabling CI;
- turning required errors into warnings;
- bypassing state-transition guards;
- creating an unconditional merge path;
- treating private repositories as secret stores;
- adding privileged credentials to Codex;
- granting Codex sudo/root;
- making `syntra-codex` a member of Docker or other privileged groups;
- embedding GitHub tokens in remote URLs;
- hard-coding the authorised Telegram user into source;
- treating AI prose as authoritative state;
- inferring human approval;
- silently ignoring reconciliation ambiguity;
- swallowing exceptions that should block a privileged action;
- expanding milestone scope to avoid a proper later implementation.

## 45. Pull Request Implementation Summary

At the end of a coding run, provide a concise structured summary containing:

- milestone/task addressed;
- material files changed;
- behaviour implemented;
- tests added/updated;
- commands/tests run;
- results;
- migrations added;
- configuration changes;
- known limitations;
- any requirement that could not be completed;
- any security-relevant change.

Do not claim CI passed unless actual CI evidence is available.

Do not claim the milestone is approved or merge-ready.

---

## 46. Definition of Coding Work Complete

A coding agent may report its assigned work complete only when:

1. the requested milestone/task is implemented within scope;
2. repository code is internally coherent;
3. required tests have been added or updated;
4. appropriate local tests/checks have been run;
5. known test failures are reported;
6. no deliberate security/control-plane rule has been bypassed;
7. no known required acceptance criterion has been silently omitted;
8. migrations/config/docs required by the change are included;
9. the worktree contains the intended source changes;
10. the final summary accurately describes what was done.

This means **coding work is complete**.

It does not mean:

- CI passed;
- Architect approved;
- human testing passed;
- Gatekeeper passed;
- the milestone is complete;
- the PR may merge.

Those are later workflow gates.

## 47. Definition of a Compliant Milestone PR

A milestone PR is compliant when, in addition to implementing the milestone:

- changes are scoped;
- tests cover new deterministic behaviour;
- existing required tests remain passing;
- schema changes include migrations;
- architectural boundaries are preserved;
- public/provider contracts are updated where required;
- security controls are not weakened;
- no real secrets are committed;
- no unapproved infrastructure dependency is introduced;
- relevant documentation is updated;
- the PR clearly explains any unavoidable follow-up.

The Architect and CI determine whether the current PR revision satisfies the complete milestone acceptance criteria.

## 49. Review Checklist for Coding Agents

Before ending a run, verify:

### Scope
- Did I implement only the assigned milestone/rework?
- Did I accidentally pre-build a future milestone?

### Correctness
- Are state transitions explicit and guarded?
- Are external side effects safe to retry/reconcile?
- Are identifiers exact rather than inferred from names?

### Tests
- Did I test success paths?
- Did I test important failure/negative paths?
- Did I run the relevant checks?

### Security
- Did I expose or log a secret?
- Did I introduce a privileged path into Codex/AI?
- Did I modify a protected path without task justification?
- Could one project access another project?

### Persistence
- Is new durable state represented explicitly?
- Does a schema change have a migration?
- Could restart leave this operation ambiguous?

### Architecture
- Did provider-specific code leak into domain/application logic?
- Did I introduce unnecessary distributed infrastructure?
- Did I make the domain depend on an external service?

### Documentation
- Did configuration, operational or contract behaviour change?
- If yes, did I update the appropriate documentation?

### Reporting
- Is my implementation summary factual?
- Have I clearly reported unresolved issues?

## 50. Final Engineering Invariants

These rules must remain true throughout development:

1. Syntra owns authoritative workflow state.
2. AI agents do not directly mutate authoritative workflow state.
3. Codex receives no privileged GitHub credentials.
4. Codex does not merge code.
5. Syntra/trusted control code owns accepted commits and pushes.
6. Syntra/trusted control code creates and manages PRs.
7. Merge requires deterministic Gatekeeper approval.
8. CI evidence is bound to the current revision.
9. Architect approval is bound to the current revision.
10. Required human approvals/tests are explicit and durable.
11. Project status is derivable from persisted state.
12. Projects are isolated.
13. Recovery reconciles before repeating uncertain privileged side effects.
14. Generated repositories are public by default unless private was explicitly approved.
15. Secrets are not committed.
16. Heavy cross-platform CI runs outside the Pi where practical.
17. Syntra Build uses Python 3.14.
18. Syntra Build source is canonical in GitHub.
19. Syntra Build self-development never means Codex directly modifies the running installation.
20. A coding agent's completion claim is advisory; tests, CI, review, human gates and Gatekeeper determine workflow completion.
